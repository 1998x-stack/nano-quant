# ADR-0001 — 模块化单体优先，先建纵向闭环

- 状态：Accepted for Phase A design（代码尚未实现）
- 日期：2026-10-27
- 项目：nano-quant

## 背景

目标同时要求 8 个金融量化模块、模块开发分支、v1.0→v2.0 迭代以及 main 的稳定集成。若直接拆出 8 个独立仓库、微服务或永久不合并的分支，将导致跨模块的时间语义、金融计算与账本协议难以统一，维护开销高。

## 决策

1. 采用一个 Git 仓库与 `src/nano_quant/` 下的领域子包（modular monolith）。
2. `core` 统一消息和时间/货币接口；模块分支用于工作隔离，文件目录才是模块的长期归属。
3. `main` 只包含通过审核的稳定集成；模块工作通过 PR 合并；每个正式发布使用不可变 Git tag。
4. v1.0 先做合成日频数据的端到端测试闭环，真实数据与复杂模型不成为初版必要阻塞。
5. 一旦未来版本证据表明单体无法满足性能、团队隔离或部署需求，再提出拆分 ADR。

## 备选方案与拒绝原因

- **每模块独立仓库**：共享数据/数学对象版本协调成本高，早期收益低。
- **每模块永久 Git 分支**：分支隔离的是整个仓库快照，不是单一目录，永久分叉引发接口漂移。
- **微服务架构**：需要网络调用、服务运维和分布式状态一致性，v1.0 没有对应需求。
- **先完成全部复杂模块再集成**：集成失败出现过晚，无法及时发现协议设计错误。

## 可验证的后果

- 通过一条 smoke / integration 测试从 DataSnapshot 产生 BacktestReport。
- CI 可检查循环依赖并运行模块边界测试。
- 所有模块输出带有固定时间语义；所有正式发布标签可重新检出。
- 代价：暂不满足分布式弹性伸缩、超低延迟或多独立团队部署要求；这些明确不在 v1.0 范围。

## 复审触发

实际观测到的容量/延迟瓶颈、权限隔离需求、跨团队独立发布需求或明确的运维问题出现时复审，而不是仅按版本号自动改架构。
