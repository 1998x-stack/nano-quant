# Git 分支、PR、发布与 main 同步规范（Phase A）

## 1. 角色与分支含义

| Ref | 作用 | 生命周期 |
| --- | --- | --- |
| `main` | **最新通过验收的稳定集成快照** | 长期 |
| `docs/phase-a-architecture` | Phase A 的架构与计划审核 | PR 合并后可删除 |
| `module/01-data` ... `module/08-execution` | 领域开发工作隔离，不是目录存储 | 任务完成后合并/删除 |
| `feature/<short-name>` / `fix/<short-name>` | 小范围增量变更 | 短期 |
| `release/v1.0` / `release/v2.0` | 发布稳定化、必要的补丁 | 按支持周期 |
| `v1.0.0` / `v1.0.1` / `v2.0.0` | 不可变发行版 Git tag | 永久 |

分支引用完整仓库的某个提交，目录组织才是长久的模块划分；模块分支应尽量短寿命，避免八个分支永远独立发展。

模块建议名称：
`module/01-data`, `module/02-finance`, `module/03-research`, `module/04-models`, `module/05-strategies`, `module/06-portfolio`, `module/07-risk`, `module/08-execution`。

## 2. 工作流程

1. 从当时最新的 `main` 创建开发分支。
2. 完成实现、文档、单测和对应的集成或 golden 测试。
3. 发起 PR，写明影响的接口、金融/时间语义、验证结果、限制及回滚方案。
4. CI 必需检查通过；如设定审核要求，则经独立审核批准后合并。
5. 合并后 `main` 成为新的已审核集成状态；删除过期的模块开发分支。
6. 若准备 v1.0 发布，从已验收集成版创建 `release/v1.0`，只允许发布稳定化和必要修复。
7. 发布检查通过后，将最终发行提交集成回 `main`，在该提交创建 `v1.0.0` 标签，并记录 release notes。
8. 补丁从相应受支持的发行维护分支修复并形成 `v1.0.1`；根据适用性把修复转移至 `main` 与后续发行线。需测试冲突，不得强制重写 main。

**重要约束**：`main` 的“最新”指最新**稳定**集成，不是最大的版本号或任何未经验证的实验代码。不得把未完成的 v2.0 直接覆盖 main。

## 3. 语义化版本的执行规则

- PATCH：向后兼容的 bug 修复。
- MINOR：向后兼容的新增特性。
- MAJOR：公开 API / 关键行为的不兼容变更。
- `v1.0.0` 表示第一版完整 v1.0 验收通过，不把 Phase A 文档标为 v1.0 正式发行。
- 数据格式、时间约定、账本语义的变化属于重要兼容性决策，必须有迁移说明。

## 4. 质量门禁

Phase A 仅检查设计文档互相一致、审查 PR diff 与验收计划；不得声称 CI/branch protection 已配置。

Phase B 建立 CI，至少执行：安装、lint、typing、单测、端到端 smoke、future-data 反事实测试和 golden 账本测试。为 `main` 启用 PR 审核/必需状态检查与禁止强推（在仓库设置和权限允许时）。支持有限协作者时可先使用适当的必需检查并记录不能强制的控制项。

## 5. 提交与 PR 模板

建议提交消息：`docs(architecture): ...`、`feat(data): ...`、`test(execution): ...`、`fix(risk): ...`。

PR 必填：
- 背景与范围 / 不在范围的事项
- 影响的 `core` 契约及依赖方向
- 输入的时间可用性与输出口径
- 执行的命令、真实结果和未运行项
- 变更对实验复现与历史版本的影响
- 发布/回滚说明

禁止以“我检查过”“应该没问题”替代可复查的测试或结果记录。
